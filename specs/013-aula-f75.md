# 013 — AULA F75 battery

**Issue**: #36

## Status: COMPLETE

## Context

An AULA F75 keyboard is on the desk spec 012 was written at, on its 2.4 GHz
receiver. Nothing in the module reads it, and nothing on the desk shows its
battery.

The receiver enumerates as `3554:fa09` ("Compx 2.4G Wireless Receiver",
after the maker of its chip). Its second interface carries a vendor
collection on usage page `0xFF02`, usage 2, with 20-byte input and output
reports numbered `0x13`, beside the keyboard, consumer, system and mouse
collections and a feature-only collection on page `0xFF04` (8 bytes). On its
cable the keyboard is a different device altogether, a Sino Wealth
`258a:010c`.

The protocol is published under MIT in PyFlat/Device-Battery-Info PR #6, with
captured replies, and in deepan-alve/womier-l65-linux for another keyboard on
the same receiver:

- Request, 20 bytes: `13 4a 00 … 00 5d` — report 0x13, command 0x4A (battery),
  an empty body, and in the last byte the sum of the nineteen before it,
  wrapping at a byte.
- Reply: report 0x13 with `(b[1] & 0x7F) == 0x4A` and a valid checksum. The
  receiver pushes other 0x13 frames unasked (a 0x0A status), so a reply is
  recognised, not merely received. `b[5]` is the level, 1–100; `b[6]` the
  power state: `0x01` on battery, `0x10` on the cable, where the level is
  pinned at 100.

Measured here, Windows 11 with the plain HID class driver: the first request
after the keyboard was physically switched from its cable to 2.4 GHz timed
out; with the link up, `13 4a 01 00 02 64 01 00 … c5` — 100 %, on battery —
answered first time, in 8 to 25 ms.

## Requirements

- R1 A driver `aula`, `Driver{Timeout}` (zero means 300 ms), `Name()` "aula".
- R2 `Find`: `hidraw.Nodes(0x3554, HasReportID(0xFF02, 0x13))`, one candidate
  per node, opening nothing. Matched by vendor and report, never by product;
  the product is the allow-list for writing: `0xFA09` → "AULA F75". Another
  product is a candidate and opening it is `ErrUnsupported` without its node
  being opened. The wired keyboard is another vendor and is never matched.
- R3 Only the battery getter is sent, as an output report on the vendor
  collection. Nothing is sent to the `0xFF04` collection.
- R4 `Batteries` drains the queue, asks, and takes the first report that
  `answers`; an unanswered question is asked once more after 200 ms. Two
  unanswered questions are no reading and no error, as for every driver's
  silent device.
- R5 `Decode`: on battery, the level (1–100) and Discharging; on the cable,
  Charging with no level (`HasLevel` false) — the battery model already has
  a reading without a level, so the pinned 100 is never shown as one. A level
  out of range or an unknown state is no reading, with the reason as the
  error. Kind keyboard; the battery's name is `battery.Product("AULA", "AULA
  F75")`, "F75".
- R6 Support: Tested on Windows (2026-10-07), Expected on Linux until a bench
  reads it there. `all` lists the driver; README, docs/credits.md (both
  sources, MIT), docs/udev.md and `packaging/60-sanshoku.rules` (vendor 3554)
  carry it.
- R7 Tests: the request bytes; `Decode` on the published captures (97 % on
  battery, cable in), the measured reply, the high bit on the command, the
  0x0A status frame, a corrupt checksum, a zero level, an unknown state; the
  retry, silence, the allow-list and a closed device on a fake; a live test.
- R8 The bench prints the tier for the system it runs on (an entry's Windows
  tier on Windows), so a device Tested on Windows is not reported there as
  Expected with a request to file an issue.

## Risks & Assumptions

- **The cable state is read as charging.** The receiver says the keyboard is
  on its cable and pins the level; whether it is charging or full is not in
  the reply. Charging with no level is the least false thing the battery
  model can say. A third state byte for "full" may exist and is no reading
  until measured.
- **One retry.** The measured miss was the first question after a switch; a
  keyboard asleep for longer may miss both and is reported silent, which a
  poller asks again on its next tick.
- **Rollback**: revert the commit; no other driver depends on it.

## Gaps found

- The first bench run on the desk read nothing — both questions unanswered,
  the keyboard presumably asleep — and the next two read 100 %. A longer or
  second retry is cheap if a poller sees it often.

## Verification

2026-10-07, Windows 11 Pro 26200, Go 1.27.0, the F75 on its receiver
`3554:fa09`:

```
aula  AULA F75 (3554:fa09)  \\?\HID#VID_3554&PID_FA09&MI_01&Col01#…  [tested]
  battery: F75  100%  discharging  keyboard (669.0 ms)
```

That run asked twice: the first question went unanswered and the second was
answered. Two earlier runs, before the bench learned to print the Windows tier,
read the same in 21.3 and 34.7 ms on the first question.

A direct exchange through the handle, six questions half a second to two and a
half seconds apart, answered each in 8 to 25 ms with `13 4a 01 00 02 64 01 …
c5`. Three questions back to back answered twice and then not at all, which
is why the driver drains and asks once more rather than asking in a loop.
